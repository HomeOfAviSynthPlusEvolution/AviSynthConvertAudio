# AviSynth — Convert Audio

[English](README.md) | [简体中文](README.zh-CN.md) | **日本語**

AviSynth — Convert Audio は、AviSynthMinus から独立した音声サンプル形式変換モジュールです。AviSynth なしでビルド・使用できるほか、静的リンクによって AviSynth コアに組み込むこともできます。整数 PCM と浮動小数点音声の相互変換に対応し、Google Highway によるクロスプラットフォームの SIMD 高速化と、フォールバック用の通常の C 実装を備えています。

Git submodule として AviSynth に組み込むことができ、単独でのテストにも対応しています。公開インターフェースは C の型と関数を使用し、内部は C++ で実装されています。AviSynth SDK、AvsCore、AvsSimd には依存しません。

## 音声変換を分離した理由

音声サンプル変換は、独立して利用・検証できる計算処理です。フレームサーバーのコアから分離することで、変換アルゴリズム、SIMD 実装、正確性テスト、ベンチマークを対象範囲の明確なプロジェクトで保守でき、ホストの内部構造への依存も減らせます。

AviSynth — Convert Audio は AviSynthMinus とともに進化します。ホストはクリップへのアクセス、スクリプトのエントリーポイント、メタデータ、音声リクエストを担当し、変換ライブラリは入力形式から出力形式への変換を担当します。直接変換するか、中間処理を経由するかは変換ライブラリが判断するため、ホストが実装の詳細に合わせて呼び出し方を変更する必要はありません。

## 対応形式

次の 5 種類のサンプル形式について、異なる形式間の全 20 通りの変換に対応しています。

| 形式 | 表現 |
|---|---|
| U8 | 符号なし 8 ビット PCM。無音値は 128 です。 |
| S16 | 符号付き 16 ビット PCM。 |
| S24 | 符号付き 24 ビット PCM。リトルエンディアンの 3 バイトに隙間なく格納します。 |
| S32 | 符号付き 32 ビット PCM。 |
| F32 | 32 ビット浮動小数点音声。 |

変換では、切り捨て、範囲外の値に対する飽和処理、NaN の無音への変換、S24 のバイト配置など、既存の AviSynth の数値処理の規則を維持します。サンプル数は各チャンネルの個々のサンプル値を数えます。例えば、ステレオの 1,024 音声フレームには 2,048 個のサンプル値が含まれます。

本プロジェクトが扱うのはサンプル形式の変換であり、サンプルレート変換、チャンネルミキシング、映像変換は行いません。これらの機能は、それぞれのモジュールで保守します。

## SIMD と CPU 制限

Highway を使用して CPU ターゲットごとの変換実装を生成し、独立した通常の C フォールバックも提供します。単独で使用する場合は、実行環境で利用可能な実装を自動選択するか、通常の C 実装を明示的に選択できます。ホストへの組み込みでは、ライブラリが実際に提供するターゲットを照会し、許可された範囲内で変換関数を選択できます。

AviSynth では、AvsSimd が環境の CPU 制限を解釈します。最終的に選択できるターゲットは、ホストが許可するターゲット、ハードウェアが対応するターゲット、変換ライブラリが実際に提供するターゲットの共通部分です。`SetMaxCPU("none")` は常に通常の C 実装を使用し、共通して利用できる SIMD ターゲットがない場合も通常の C 実装にフォールバックします。

ターゲットは利用側のインスタンスごとに選択し、Highway のグローバルなターゲット制限は変更しません。統合用インターフェースでは Highway のターゲットビット値を直接使用します。バージョン間で存在しない、または認識できないターゲットは選択対象から除外し、未対応のターゲットを明示的に要求した場合は失敗を返します。

## ビルドと統合

本プロジェクトは CMake を使用し、C++17 対応のコンパイラーを必要とします。通常の利用向けインターフェースは C の型と関数を使用し、C++ クラス、STL コンテナー、Highway のベクトル型を公開しません。C++ 例外がインターフェースの境界を越えることもありません。

主な統合方法は、ホストのリポジトリで Git submodule として本プロジェクトのバージョンを固定し、CMake で一緒にビルドする方式です。変換ライブラリとその依存関係は静的ライブラリのターゲットとしてリンクし、依存関係は CMake が伝播します。ホストがカーネルのソースファイルを直接コンパイルしたり、列挙したりする必要はありません。

単独ビルドでは固定バージョンの Highway を使用し、基準バージョンは 1.4.0 です。ホストと一緒にビルドする場合は、ホストが提供する互換性のある `hwy` ターゲットを再利用し、依存ライブラリの重複ビルドを避けます。AvsSimd は AviSynth リポジトリに残し、変換ライブラリは Highway に直接依存します。

インターフェースは AviSynthMinus とともに変更される場合があります。C インターフェースは統合を容易にしますが、異なるバージョンのビルド済みライブラリを自由に置き換えられることを保証するものではありません。更新時は、対応するヘッダーとライブラリを組み合わせて使用してください。

CMake ターゲットは `AviSynth::ConvertAudio`、静的ライブラリ名は `AudioConvert` です。

## テストと性能

カーネルの正確性テストとベンチマークは、AviSynth を読み込まずに単独で実行できます。テストでは、形式間の変換結果、数値の境界、特殊な浮動小数点入力、端数を含むサンプル数、バッファー境界を確認します。AviSynth リポジトリの統合テストでは、公開フィルターのエントリーポイント、音声リクエストの動作、映像のパススルーを検証します。

2026-09-06 時点で、パラメーター展開後のテスト数は C インターフェースのスモークテストを含めて **596 件**です。ローカルの Windows x64 環境で、MSVC、clang-cl、通常の C 実装のみの各構成ですべて合格しています。

以下は、1 回につき **65,536 個のサンプル値（64K）**を変換した native 性能結果の一部です。時間の単位は **μs/呼び出し**です。比較対象は **AviSynth+ 3.7.5** に限定しており、上流の後続バージョンを対象とした結果ではありません。

| 変換 | AviSynth+ 3.7.5 native | Convert Audio native | 高速化率 |
|---|---:|---:|---:|
| S16 → F32 | 3.173 | 3.178 | 1.00× |
| F32 → S16 | 4.561 | 4.494 | 1.01× |
| S24 → F32 | 6.853 | 5.923 | 1.16× |
| F32 → S24 | 9.311 | 5.425 | 1.72× |
| S32 → F32 | 4.498 | 4.496 | 1.00× |
| F32 → S32 | 4.393 | 4.495 | 0.98× |
| U8 → S16 | 2.102 | 1.617 | 1.30× |
| U8 → S32 | 4.281 | 2.696 | 1.59× |
| S32 → U8 | 3.193 | 2.692 | 1.19× |

測定日は 2026-09-06、環境は AMD Ryzen 9 7940H、Windows x64、clang-cl 22.1.3 です。両実装とも Release /O2、LTO 無効でビルドし、同じ論理プロセッサーに固定して実行しました。元のカーネルは AviSynth+ 3.7.5（`6c7c2661`）、本モジュールは `16259ac5` を使用しています。それぞれ利用可能な native 実装を使用し、原版は変換経路に応じて SSE2、SSSE3、AVX2、本モジュールは Highway の `AVX3_ZEN4` を自動選択しました。

計測する各バッチで 50,000 回変換し、7 ラウンド測定して各実装の所要時間の中央値を採用しました。各バッチで 100 回のウォームアップを行い、原版、本モジュール、通常の C 基準実装の計測順を入れ替えています。全 20 経路で、計測に使用した入力に対する出力がバイト単位で一致することを確認しました。原版の S24↔F32 は S32 を経由する 2 段階の処理を含み、バッファーと中間領域は事前に確保して再利用しています。

高速化率は原版の所要時間を本モジュールの所要時間で割った値で、1 を超えると本モジュールの方が高速です。計測対象は変換カーネルのみで、メモリー確保、関数選択、ホストによる読み込みは含みません。これは 7 ラウンドからなる 1 回の測定結果であり、数パーセントの差を安定した性能向上や低下と見なすべきではありません。

性能比較では、コンパイラー、ビルドオプション、入力データ、CPU 制限を揃え、サンプル数と計測範囲を明示してください。カーネルの処理時間とフィルター全体の処理時間は別々に測定し、ホストによる読み込みやバッファー管理などのコストがアルゴリズムの比較に混在しないようにします。SIMD ターゲットの幅が広くても、すべての変換経路で高速になるとは限りません。実装の判断は測定結果に基づいて行います。
